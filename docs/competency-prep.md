Этот файл — шпаргалка для защиты/демонстрации проекта по трём темам. Для каждой темы: что именно
сделано в проекте (с путями к файлам, чтобы можно было открыть и показать), как это продемонстрировать
живьём, вопросы по проекту с ответами, и отдельно — общие вопросы по теме (не привязанные к проекту),
которые могут спросить вообще.

Проект: `ClipGen.Be` — backend-блок Jobs/Clips/Tags на ASP.NET Core 10 / EF Core 10 / Dapper / JWT.
Контекст решений — `docs/data-layer-plan.md`, итоги тестов и trade-off'ы — `docs/data-access-notes.md`,
статус этапов — `docs/plan.md`.

## Тема 1. Use integration test approaches, strategies and methodologies

### Что сделано

**Где:** `tests/ClipGen.Be.IntegrationTests/`.

**Подход.** Тесты — не unit-тесты с моками, а настоящие HTTP-интеграционные тесты через
`WebApplicationFactory<Program>` (`Microsoft.AspNetCore.Mvc.Testing`): поднимается весь реальный
стек приложения в памяти — маршрутизация, весь middleware pipeline (аутентификация, авторизация,
обработка исключений), настоящий DbContext — и бьётся настоящая SQL Server база (`ClipGenDb_Test`
на LocalDB). Это чёрный ящик на уровне HTTP-контракта: тест видит то же самое, что увидел бы реальный
клиент (статус-коды, JSON), а не внутренние вызовы методов.

**Почему так, а не unit-тесты.** Задача — проверить, что компоненты системы работают **вместе**:
контроллер → фильтр владения → доменная модель → EF Core → SQL Server → обратно в JSON. Для такого
тонкого CRUD-слоя юнит-тесты с моками DbContext почти ничего не поймали бы (нашли баги были именно
на стыке EF Core ↔ SQL Server ↔ сериализация, а не в изолированной бизнес-логике).

**Стратегия изоляции тестов:**
- `CustomWebApplicationFactory` (`tests/.../Infrastructure/CustomWebApplicationFactory.cs`) переопределяет
  конфигурацию (`ConfigureWebHost`/`UseSetting`): отдельная строка подключения (`ClipGenDb_Test`, с
  возможностью подставить другую через переменную окружения `CLIPGEN_TEST_CONNECTION` — то есть тесты
  гоняются и на Azure SQL без изменения кода), свой JWT-ключ, свои учётные данные тестового админа.
  Это ключевой момент методологии: тесты **не зависят** от личных `user-secrets` разработчика и
  воспроизводимы на любой машине/в CI «из коробки».
- `DatabaseFixture` (`IAsyncLifetime` + `[CollectionDefinition("Database")]`) мигрирует тестовую БД
  один раз на весь прогон; все 6 классов тестов используют `[Collection("Database")]` — xUnit гоняет их
  последовательно (не параллельно), чтобы не было гонки за одну БД/миграцию.
- Изоляция между тестами — не транзакции и не очистка, а **уникальные данные** (имена пользователей,
  файлов, тегов с `Guid` в имени). Простое решение, осознанно выбранное вместо инфраструктуры откатов —
  обосновано и описано как ограничение в `docs/data-access-notes.md`.

**6 классов тестов (13 тестов) — покрытие по компонентам, границам и потокам данных:**

| Класс | Что проверяет | Чьи компоненты сходятся |
|---|---|---|
| `AuthFlowTests` | register → login → `/me`; без токена / с испорченным токеном → 401 | Identity + JWT middleware + контроллер |
| `JobStorageTests` | round-trip `ProcessingOptions` (включая вложенный `CropSettings`) через JSON-колонку; обновление опций | Контроллер + EF Core + SQL Server JSON-колонка |
| `ClipAndCascadeTests` | add/update/delete клипа; повторное удаление → 404; каскадное удаление клипов при удалении задачи | Домен (`Job.AddClip`) + EF Core cascade + SQL Server FK |
| `TagSharingTests` | общий тег выживает при удалении одной из двух задач; замена набора тегов (keep/drop/add) | N–N через явную `JobTag`, `NoAction` на `Tag` |
| `OwnershipBoundaryTests` | чужой пользователь → 404 на read/update/delete, не видит задачу в списке | `JobOwnershipFilter` — внешняя граница (кто смеет видеть чьи данные) |
| `AdminReportTests` | обычный пользователь → 403, анонимный → 401, админ видит данные всех пользователей | Ролевая авторизация + Dapper read-путь |

Это прямое покрытие формулировки outcome: «interaction paths» (auth→domain→DB), «external boundaries»
(ownership, роли), «data flows» (CRUD, N–N, каскады).

**Анализ результатов и выявленные дефекты — задокументировано в `docs/data-access-notes.md`, раздел 2.**
Тесты не просто написаны и прошли с первого раза — ими реально нашли 4 дефекта:
1. `DbUpdateConcurrencyException` при добавлении клипа — EF Core выбрал `UPDATE` вместо `INSERT` для
   новой сущности с клиентским `Guid`-ключом (навигационный fixup без явного `Add`). Исправлено
   `ValueGeneratedNever()`.
2. Enum сериализовался как число, а не строка — несовпадение ожиданий клиента/сервера.
3. Риск конфликта отслеживания EF Core при замене тегов (два объекта с одним составным ключом) —
   исправлено мутацией коллекции в месте, а не присвоением нового списка.
4. Порядок старта `WebApplicationFactory`: обращение к `Factory.Services` стартовало весь хост
   (включая сид ролей) раньше, чем успевала выполниться миграция тестовой БД — «Cannot open database».

Каждый дефект — с первого прогона тестов, с конкретной причиной и конкретным фиксом, и после фикса
тест прошёл и стал регрессионной защитой от повторения. Это и есть «Analyze test results to identify
integration defects and adjust test coverage».

**Корректировка покрытия:** `OwnershipBoundaryTests` — отдельный класс, выделенный специально, потому
что фильтр владения — область, где код «выглядит правильным», но ошибка проявляется только при
реальном обращении от имени другого пользователя; решили проверить явно, а не полагаться на то, что
остальные тесты её случайно покроют.

### Как показать живьём

```
dotnet test tests/ClipGen.Be.IntegrationTests
```
13 тестов, все зелёные, ~2 секунды. Можно открыть `docs/data-access-notes.md` и показать раздел про
найденные дефекты — это самый сильный аргумент («не просто написал тесты, а ими реально что-то нашёл»).

### Вопросы по проекту

**В: Почему тесты через `WebApplicationFactory`, а не через мок `DbContext` (in-memory provider)?**
О: In-memory провайдер EF Core не умеет JSON-колонки и многие SQL Server-специфичные вещи (как раз
то, где нашлись реальные баги — `ValueGeneratedNever`, сериализация). Настоящая SQL Server база даёт
уверенность, что в продакшене будет работать так же, как в тесте.

**В: Как тесты не мешают друг другу, если БД общая?**
О: Каждый тест генерирует уникальные данные (`Guid` в имени пользователя/файла/тега), поэтому даже
при последовательном прогоне по общей БД они не пересекаются. Явной очистки нет — тестовая БД
одноразовая и это не проблема.

**В: Почему тесты идут последовательно, а не параллельно?**
О: Один `[CollectionDefinition]`/`ICollectionFixture` на весь набор — xUnit гарантирует, что тесты
внутри одной коллекции не запускаются параллельно. Иначе была бы гонка за миграцию БД в момент старта.

**В: Что если тест нужно гонять в CI, где нет доступа к личным секретам разработчика?**
О: Для этого и сделан `CustomWebApplicationFactory` — он сам прокидывает тестовый JWT-ключ и
тестовые данные админа через `UseSetting(...)`, не трогая `user-secrets` разработчика.

**В: Какой тип тестов это — integration, system, e2e?**
О: Integration на уровне API: реальный процесс приложения + реальная БД, но без реального сетевого
транспорта (`WebApplicationFactory` создаёт `HttpClient` в памяти) и без фронтенда/браузера — то есть
не полноценный e2e, но больше чем «интеграция двух классов».

**В: Как бы вы добавили тест на конкурентную запись (race condition)?**
О: Два параллельных HTTP-запроса на изменение одного и того же клипа через `Task.WhenAll`, и проверка,
что финальное состояние согласовано (или что один из запросов получил ожидаемую ошибку конкурентности).
В текущем наборе это сознательно не покрыто — отмечено как ограничение в заметке.

### Общие вопросы (не по проекту)

**В: Чем integration-тест отличается от unit-теста?**
О: Unit-тест проверяет один компонент в изоляции (зависимости — моки/стабы), быстрый и детерминированный.
Integration-тест проверяет, что несколько реальных компонентов (БД, очередь, внешний сервис) работают
вместе правильно — медленнее, но ловит баги на стыках, которые моки принципиально не видят.

**В: Что такое test pyramid и почему он так называется?**
О: Модель распределения тестов по уровням: много быстрых unit-тестов в основании, меньше
integration-тестов в середине, совсем немного e2e на вершине — потому что e2e медленные, хрупкие и
дорогие в поддержке. Форма пирамиды — про соотношение количества, не про важность.

**В: Mock vs Stub vs Fake vs Spy — в чём разница?**
О: Stub — возвращает заранее заданные ответы, без проверки вызовов. Mock — то же самое, но ещё
проверяет, что его методы были вызваны ожидаемым образом (verify). Fake — рабочая, но упрощённая
реализация (например, in-memory БД вместо настоящей). Spy — настоящий объект, который дополнительно
запоминает, как его вызывали.

**В: Что такое flaky test и как с ним бороться?**
О: Тест, который иногда проходит, иногда падает без изменений в коде — обычно из-за гонок, таймингов,
общего состояния между тестами или зависимости от внешних сервисов. Лечится изоляцией данных,
детерминированными ожиданиями вместо `sleep`, явными ретраями только там, где это оправдано бизнесом,
и — если неизбежно — изоляцией «плохого» теста в отдельный прогон, а не игнорированием молча.

**В: Что такое Arrange-Act-Assert?**
О: Структура теста из трёх частей: подготовка данных/состояния (Arrange), выполнение проверяемого
действия (Act), проверка результата (Assert). Помогает читать тест как историю, а не как кашу.

**В: Как тестировать внешние интерфейсы (external boundaries), если внешний сервис недоступен в тестах?**
О: Контрактное тестирование (contract testing, например Pact) — фиксируется контракт запрос/ответ,
обе стороны (consumer и provider) тестируются против него независимо, без необходимости поднимать
настоящий внешний сервис в каждом прогоне. Либо — тестовый double/sandbox-окружение, которое
предоставляет сам внешний сервис.

**В: Что важнее — покрытие кода (code coverage) или качество тестов?**
О: Высокое покрытие не гарантирует отсутствие багов (можно выполнить строку кода и не проверить
результат). Покрытие — сигнал «куда ещё не дошли», а не цель. Правильный вопрос — покрыты ли
ключевые пользовательские сценарии и граничные случаи, а не процент строк.

**В: Как интегрировать интеграционные тесты в CI/CD?**
О: Отдельный job/стадия, поднимающая зависимости (БД, очереди) — через Docker/Testcontainers или
выделенный тестовый инстанс, прогон после unit-тестов (они дешевле и быстрее — fail fast), результаты
как gate перед деплоем; часто интеграционные тесты гоняют не на каждый commit, а на PR/merge из-за
их длительности.

## Тема 2. Apply security practices and approaches to protect the application with framework

### Что сделано

**Аутентификация — ASP.NET Core Identity + JWT.** `src/ClipGen.Be.Host/Program.cs`:
`AddIdentityCore<AppUser>().AddRoles<IdentityRole<Guid>>().AddEntityFrameworkStores<AppDbContext>()
.AddDefaultTokenProviders()`. Пароли хранятся только как хэш (Identity `PasswordHasher`, PBKDF2),
сырой пароль нигде не логируется и не сохраняется — виден только внутри `UserManager.CreateAsync`/
`CheckPasswordAsync` (`Controllers/AuthController.cs`). Политика сложности пароля — стандартная
встроенная (цифра/регистр/спецсимвол/длина), не отключена и не ослаблена.

Выдача токена — `Auth/TokenService.cs`: JWT подписывается `SymmetricSecurityKey` (HMAC SHA256),
claims — `NameIdentifier`, `Name`, по одному `Role` на роль. Приём и проверка — встроенный
`Microsoft.AspNetCore.Authentication.JwtBearer`, `TokenValidationParameters` проверяет issuer,
audience, подпись и срок действия — это всё framework-код, не самописный парсинг токена.

**Авторизация — на двух уровнях.**
- Ролевая, framework-политиками: `AddAuthorizationBuilder().AddPolicy("AdminOnly",
  p => p.RequireRole("Admin"))`; `[Authorize]` по умолчанию на `ApiControllerBase`, `[AllowAnonymous]`
  только на `register`/`login`, `[Authorize(Policy = "AdminOnly")]` на `AdminController`.
- Ресурсная (чьи это данные) — `Filters/JobOwnershipFilter.cs` и `ClipOwnershipFilter.cs`:
  `IAsyncActionFilter` — framework-точка расширения MVC pipeline, регистрируются в DI
  (`AddScoped`) и подключаются декларативно (`[ServiceFilter(typeof(...))]`). Возвращают **404**,
  а не 403 — осознанно, чтобы не подтверждать существование чужого ресурса (anti-enumeration).

**Валидация входных данных — тоже через framework, не ручными `if`.** `[ApiController]` сам
валидирует DTO и возвращает `400 ValidationProblemDetails`. Встроенные атрибуты (`[Required]`,
`[Range]`, `[StringLength]`, `[EnumDataType]`) и свои (`Contracts/Validation/`):
- `UserLoginAttribute` — логин: латиница/цифры/`._-`, 3–32 символа, запрет `admin/root/system`
  (`[GeneratedRegex]` с таймаутом — защита от катастрофического бэктрекинга).
- `TagNamesAttribute` — имя тега: буквы/цифры/пробел/дефис.
- `ClipRangeAttribute` — класс-левел атрибут, кросс-полевая проверка (конец > начала, 1–180 сек).
- `ProcessingOptionsDto : IValidatableObject` — смещение кадрирования валидно только при
  `ManualOffset`.

**Защита данных / частые уязвимости:**
- **SQL-инъекции.** Весь путь записи — EF Core LINQ (параметризуется автоматически). Единственный
  raw SQL (`Reports/JobReportsQueries.cs`, Dapper) — без единого пользовательского ввода в строке
  запроса (нет ни одного `WHERE` с параметром от клиента) — инъекции там структурно невозможны.
- **Секреты не в репозитории.** `Jwt:SigningKey` — пустая строка-плейсхолдер в `appsettings.json`,
  реальное значение — только в `dotnet user-secrets` (вне git). Строка подключения к LocalDB — не
  секрет (без пароля, `Trusted_Connection`), поэтому допустимо в `appsettings.Development.json`;
  при переходе на Azure SQL — тоже через секреты, без изменения кода.
  Утечка этого конкретного ключа — критична (позволяет подделать любой токен, включая админский),
  в отличие от беспарольной строки LocalDB — поэтому именно он выделен как секрет, а не всё подряд.
- **Раскрытие информации через ошибки.** `AddProblemDetails()` + `app.UseExceptionHandler()` —
  необработанные исключения не показывают стектрейс наружу (framework default вне Development).
- **Enumeration / information disclosure через авторизацию.** См. выше про 404 вместо 403 в
  ownership-фильтрах.

**«Review and update existing code to address identified security gaps» — конкретные решения по ходу:**
- Изначально предполагалась cookie-аутентификация с antiforgery (ближе к схеме всего продукта),
  но для этого изолированного API-блока осознанно перешли на JWT — проще тестировать через Swagger,
  без ручного проставления XSRF-заголовка на каждый мутирующий запрос.
- Сидирование админ-аккаунта — **не** публичный endpoint «стать админом», а конфигурационный сид,
  включённый только в Development и только если заданы `Seed:AdminUserName`/`Seed:AdminPassword` —
  моделирует то, как администраторы реально создаются в продукте (вручную, не самостоятельная
  регистрация).

### Как показать живьём

Swagger (`/swagger`): `POST /api/auth/register` → `POST /api/auth/login` (скопировать token) →
кнопка Authorize → `GET /api/jobs` работает; без Authorize — `401`; под обычным пользователем
`GET /api/admin/jobs-summary` — `403`. Показать `appsettings.json` с пустым `Jwt:SigningKey` и
`dotnet user-secrets list` в `ClipGen.Be.Host` — реальный ключ не в файле.

### Вопросы по проекту

**В: Почему JWT, а не cookie, если остальной продукт по спеке — на cookie?**
О: Это изолированный API-блок, тестируемый через Swagger — JWT с кнопкой Authorize проще и
нагляднее для демонстрации, чем cookie + antiforgery token, который неудобно вручную прокидывать
через Swagger UI. Явно задокументированное отклонение от общей архитектуры продукта, с обоснованием.

**В: Почему ownership-фильтр возвращает 404, а не 403?**
О: 403 подтверждает: «ресурс существует, но тебе нельзя» — для злоумышленника это утечка информации
(можно перебором узнавать, какие ID существуют). 404 не различает «не существует» и «не твоё».

**В: Как защищена JWT подпись от подделки?**
О: `TokenValidationParameters.ValidateIssuerSigningKey = true` + симметричный ключ, которого нет
в репозитории (только в user-secrets/проде — в секрет-хранилище). Без ключа невозможно подписать
валидный токен, и сервер отклонит токен с неверной подписью (это framework-проверка, не наша).

**В: Что если кто-то украдёт JWT? Как отозвать токен до истечения срока?**
О: В текущей реализации — никак, токен stateless и живёт до `ExpiryMinutes`. Для настоящего revoke
нужен был бы черный список токенов (БД/Redis) или переход на short-lived access + refresh token
с возможностью отозвать refresh. Сознательно не реализовано — вне скоупа этого блока.

**В: Почему валидация в DTO, а не в контроллере/сервисе?**
О: `[ApiController]` автоматически гоняет `ModelState` до того, как код action выполнится — это
framework-механизм, который даёт единообразный `400 ValidationProblemDetails` без ручного кода
проверки в каждом методе. Бизнес-проверки, которые нельзя выразить атрибутом (например, принадлежит
ли клип задаче), — уже в фильтрах/контроллере.

**В: Как обрабатывается brute-force по паролю?**
О: Защита приходит от самой библиотеки Identity (поддержка lockout после N неудачных попыток
встроена в `UserManager`/`SignInManager`), но в данном блоке используется `CheckPasswordAsync`
напрямую без включённого `SignInManager`-флоу с lockout — то есть в текущем виде лимит попыток не
подключён явно. Честный ответ на этот вопрос — это зона для улучшения, не заявленная как готовая.

### Общие вопросы (не по проекту)

**В: Authentication vs Authorization — в чём разница?**
О: Authentication — «кто ты» (подтверждение личности). Authorization — «что тебе можно» (права
после того, как личность подтверждена). Можно быть аутентифицированным и не иметь прав на конкретное
действие.

**В: Назовите основные уязвимости из OWASP Top 10 и способы защиты.**
О: Broken Access Control (проверка прав на каждом ресурсе, не только в UI), Injection (параметризация
запросов), Cryptographic Failures (не хранить секреты в коде, шифровать at rest/in transit),
Security Misconfiguration (безопасные дефолты фреймворка, не выключать защиты), Vulnerable Components
(обновлять зависимости, сканировать на известные CVE), Authentication Failures (политика паролей,
MFA, lockout), и т.д. — суть ответа: framework-защиты включены по умолчанию и не отключаются без
веской причины.

**В: SQL injection — как работает атака и как защититься?**
О: Атакующий подставляет в поле ввода фрагмент SQL, который меняет смысл запроса (например,
`' OR 1=1 --`), если запрос собирается конкатенацией строк. Защита — параметризованные запросы/ORM
(значение передаётся как параметр, а не как часть текста SQL), никогда не строить SQL из
необработанного пользовательского ввода.

**В: XSS vs CSRF — в чём разница?**
О: XSS (Cross-Site Scripting) — атакующий внедряет свой JS-код на страницу, который выполняется в
браузере жертвы (через невалидированный ввод, который попадает в HTML как есть). CSRF (Cross-Site
Request Forgery) — атакующий заставляет браузер жертвы отправить легитимный запрос (с её cookie) на
сторонний сайт без её ведома. Защита от XSS — экранирование вывода; от CSRF — anti-forgery token или
`SameSite` cookie.

**В: Почему не стоит хранить JWT в localStorage?**
О: localStorage доступен из JS — если на странице сработает XSS, токен украдут. HttpOnly cookie
недоступна JS, но тогда нужна защита от CSRF (SameSite/antiforgery). Абсолютно безопасного места нет —
это компромисс, выбор зависит от модели угроз конкретного приложения.

**В: HS256 vs RS256 для подписи JWT — когда что?**
О: HS256 — один общий секретный ключ и для подписи, и для проверки (симметричный) — подходит, когда
подписывает и проверяет один и тот же сервис. RS256 — асимметричный (приватный ключ подписывает,
публичный проверяет) — нужен, когда проверяющих сервисов много и им нельзя доверить секрет подписи
(например, микросервисы, которым достаточно публичного ключа).

**В: Что такое принцип наименьших привилегий (least privilege)?**
О: Любой компонент/пользователь/процесс должен иметь ровно тот минимум прав, который нужен для его
задачи — не больше. Снижает блast radius при компрометации: взломанный компонент с минимальными
правами не может натворить столько, сколько компонент с правами администратора.

**В: Чем отличается хэширование пароля от шифрования?**
О: Шифрование обратимо (есть ключ, который расшифрует обратно). Хэширование — односторонняя функция,
исходное значение не восстановить из хэша. Пароли всегда хэшируют (с солью, через медленные
алгоритмы вроде bcrypt/Argon2/PBKDF2), а не шифруют — так даже разработчик/утечка БД не даёт пароль
в открытом виде.

**В: Что такое defense in depth?**
О: Несколько независимых слоёв защиты, а не один «главный замок» — если один слой пробит, следующий
всё равно останавливает атаку (например: валидация входа + параметризация SQL + авторизация на
ресурсе + сетевые ограничения + аудит-логи — каждый по отдельности мог бы быть пробит).

## Тема 3. Use engines for database interaction *(ключевая — Key: Yes)*

### Что сделано

**Два движка в одном проекте, каждый — там, где он сильнее.**

**EF Core (ORM)** — основной движок для всей записи и графовых операций.
- `ClipGen.Infrastructure/Data/AppDbContext.cs` — `IdentityDbContext<AppUser, IdentityRole<Guid>, Guid>`.
- Конфигурация — **только Fluent API** (`Data/Configurations/*.cs`), не data annotations — осознанное
  разделение: атрибуты — для валидации DTO (слой API), Fluent API — для маппинга на БД (слой данных).
- **Связи:**
  - 1–N: `AppUser → Job`, `Job → Clip` (`JobConfiguration.cs`: `HasOne`/`HasMany` + `OnDelete`).
  - N–N: `Job ↔ Tag` через **явную** join-сущность `JobTag` (`JobTag.cs`), а не неявную
    skip-navigation EF Core — осознанный выбор, чтобы явно управлять каскадом по каждой стороне
    отдельно (`Job → JobTag` каскадно, `Tag → JobTag` — `NoAction`, тег переживает удаление связи).
- **Нетривиальные колонки:**
  - JSON-колонка: `builder.ComplexProperty(j => j.Options).ToJson()` — весь `ProcessingOptions`
    вместе с вложенным `CropSettings` хранится как один JSON-столбец (EF Core 8+ JSON columns).
  - Complex type без JSON: `TimeRange` (`Clip.Range`) — два обычных столбца `RangeStart`/`RangeEnd`
    (`ComplexProperty` без `.ToJson()`) — показывает разницу между «структурный тип как JSON» и
    «структурный тип как плоские столбцы», и когда что выбрать (JSON — для гибких/вложенных опций,
    плоские столбцы — для двух значений, которые всегда нужны вместе и участвуют в индексах/фильтрах).
- **Каскады настроены по правилу «одна каскадная ветка», требование SQL Server** (нельзя несколько
  путей каскада к одной таблице): `AppUser → Job → (Clip, JobTag)` — каскадно; `Tag`, остальное —
  `NoAction`. Настроено явно в `JobConfiguration.cs`/`ClipConfiguration.cs`/`TagConfiguration.cs`/
  `JobTagConfiguration.cs`.
- **Миграции — код, не ручной SQL:** `dotnet-ef` как **локальный** инструмент репозитория
  (`.config/dotnet-tools.json`, не требует глобальной установки). `InitialCreate` — первая схема;
  `FixGuidKeyGeneration` — вторая, с нулевым SQL-дифом (чисто метаданные EF Core, см. ниже).
- **Инкапсуляция:** у `Job`/`Clip`/`Tag` — приватные сеттеры, изменение состояния только через методы
  домена (`Job.Create`, `Job.AddClip`, `Job.ReplaceTags`, `Clip.ApplyTimecodes`); EF Core маппит
  приватные сеттеры штатно через reflection, бизнес-инварианты не обходятся через голые свойства.

**Dapper (micro-ORM)** — для одного конкретного read-пути, где ORM неудобен.
- `ClipGen.Infrastructure/Reports/JobReportsQueries.cs` — `GET /api/admin/jobs-summary`:
  кросс-пользовательский отчёт (не один агрегатный корень, а плоская проекция по всем `Job` всех
  пользователей) — через EF Core это было бы либо без `Include` (эквивалент ручного SQL, но менее
  читаемо), либо N+1-запросы. Один явный SQL читается и поддерживается проще для такого случая.
- **Trade-off, пойманный и исправленный в процессе:** первая идея — один `LEFT JOIN Clips` +
  `LEFT JOIN JobTags/Tags` + `GROUP BY` + `STRING_AGG`. Отклонена: `Clips` и `Tags` — два независимых
  «один-ко-многим» от `Jobs`, совместный `LEFT JOIN` даёт декартово произведение (клип × тег), что
  задвоило бы имена тегов на количество клипов. Решение — **два коррелированных скалярных подзапроса**
  вместо одного JOIN. Проверено вживую: 1 клип + 2 тега → отчёт отдал `clipCount: 1` и оба тега без
  дублей, без побочных эффектов.
- Общая строка подключения с EF Core — одна конфигурация (`DependencyInjection.cs`), два движка
  регистрируются рядом через DI (`AddDbContext` + `AddScoped<IDbConnection>`).

**Trade-off, найденный через понимание механики движка (не поверхностное использование):**
`DbUpdateConcurrencyException` при добавлении клипа — EF Core для сущности с клиентским `Guid`-ключом,
достигнутой через fixup навигации (без явного `db.Clips.Add(...)`), не был уверен, кто генерирует
ключ, и выбрал `UPDATE` вместо `INSERT`. Разобрался в механике генерации ключей EF Core, исправил
`ValueGeneratedNever()` на `Id` у `Job`/`Clip`/`Tag` (их GUID всегда генерируются в домене, не в БД).
Проверил гипотезу: сгенерированная миграция `FixGuidKeyGeneration` оказалась пустой (без единой
строки SQL) — подтвердило, что дело было именно в допущениях change tracking, а не в структуре таблиц.

**Транзакции** — осознанное решение. `SaveChangesAsync()` у EF Core сама атомарна на уровне одного
вызова; удаление `Job` **не** оборачивается в явный `BeginTransaction`/`Commit` — каскад `Clip`/`JobTag`
происходит на уровне SQL Server (`ON DELETE CASCADE`) в рамках одного DELETE-statement, этого
достаточно для атомарности. Явная транзакция была бы избыточным усложнением без функциональной
выгоды — но это решение, которое нужно уметь objяснить, а не просто «забыли».

### Как показать живьём

`src/ClipGen.Infrastructure/Data/Configurations/JobConfiguration.cs` — показать `ComplexProperty(...).ToJson()`

### Вопросы по проекту

**В: Почему N–N сделана через явную сущность `JobTag`, а не через встроенную skip-navigation EF Core?**
О: Явная сущность даёт полный контроль над каждой стороной связи отдельно — в частности, разные
правила удаления (`Job → JobTag` каскадно, `Tag → JobTag` — нет). Через неявную skip-navigation EF Core
такое по-другому настраивается и менее прозрачно читается в коде.

**В: В чём разница между JSON-колонкой (`Options`) и complex type (`Range`) — почему не оба через JSON?**
О: `ProcessingOptions` — гибкая, вложенная структура, к которой не нужны SQL-фильтры/индексы по
отдельным полям — JSON уместен. `TimeRange` — ровно два значения, которые логически всегда идут
парой и могли бы участвовать в диапазонных запросах/индексах — плоские столбцы читаемее в SQL
напрямую (например, при ручном SQL-анализе в БД) и дешевле по месту, чем JSON-обёртка для двух чисел.

**В: Как вы поняли, что проблема именно в генерации ключа, а не где-то ещё?**
О: Включено логирование SQL EF Core — в логе буквально было видно `UPDATE [Clips] SET ...` вместо
ожидаемого `INSERT INTO [Clips] ...` для только что созданной сущности. Это прямо указывает на то,
что EF Core посчитал сущность уже существующей (Modified), а не новой (Added).

**В: Почему не оставить всё через EF Core — зачем вообще Dapper, если он добавляет второй движок?**
О: `Admin`-отчёт — кросс-пользовательский, не укладывается в модель «загрузить агрегат через
навигации». Можно было бы и через EF (`.Select()` без `Include`, с подзапросами в LINQ), но явный SQL
для такого разового отчёта читается прямее и не тащит накладные change tracking, которые здесь не
нужны ни для чего (данные только читаются, не изменяются).

**В: Что будет, если убрать `ValueGeneratedNever()`?**
О: Для путей, где сущность создаётся через явный `db.Set<T>().Add(...)` (как `Job` в
`JobsController.Create`), ничего не изменится — EF правильно определит `Added`. Баг проявляется
только там, где сущность попадает в трекер через fixup навигации без явного `Add` — как было с
`Clip` через `Job.AddClip`.

**В: Почему миграции — локальный инструмент (`dotnet-ef` в `.config/dotnet-tools.json`), а не
глобальная установка?**
О: Версия `dotnet-ef` фиксируется в репозитории и совпадает у всех, кто клонирует проект (и в CI) —
не зависит от того, что стоит глобально на чьей-то машине. `dotnet tool restore` — и всё готово.

**В: Как бы вы перешли с LocalDB на Azure SQL — что меняется в коде?**
О: Ничего в коде — провайдер (`UseSqlServer`) один и тот же для LocalDB и Azure SQL, меняется только
строка подключения в конфигурации (и добавляется `EnableRetryOnFailure`, который уже включён заранее
и на LocalDB просто никогда не срабатывает).

### Общие вопросы (не по проекту)

**В: ORM vs micro-ORM vs raw ADO.NET — когда что выбирать?**
О: Raw ADO.NET — максимальный контроль и производительность, но весь маппинг и управление
соединениями — руками. Micro-ORM (Dapper) — убирает боль маппинга результата в объекты, но SQL
пишете сами — хорош для чтения/отчётов и мест, где важен контроль над запросом. Полноценный ORM
(EF Core) — даёт change tracking, миграции, навигации, LINQ — хорош для написания бизнес-логики
над графом сущностей, платите накладными расходами и меньшим контролем над итоговым SQL.

**В: Что такое проблема N+1 и как её избежать?**
О: Когда для списка из N записей на каждую отдельно выполняется дополнительный запрос к связанным
данным — итого N+1 запросов вместо одного. Решается eager loading (`Include` в EF Core) или явным
JOIN/проекцией, которая сразу тащит нужные данные одним запросом.

**В: Lazy loading vs eager loading — трейд-оффы?**
О: Lazy — связанные данные подгружаются по факту обращения к навигационному свойству — удобно, но
легко случайно получить N+1 и не заметить. Eager (`Include`) — данные грузятся сразу, явно и
предсказуемо, но можно перетащить больше данных, чем нужно, если не выбирать аккуратно.

**В: Что такое optimistic vs pessimistic concurrency control?**
О: Pessimistic — блокировка строки на время транзакции (другие ждут или получают ошибку сразу).
Optimistic — никто не блокирует, но при сохранении проверяется, не изменил ли кто-то данные с
момента чтения (через версию/timestamp/rowversion) — если изменил, сохранение отклоняется и клиент
должен перечитать и повторить.

**В: Что такое ACID?**
О: Atomicity (транзакция выполняется целиком или не выполняется вовсе), Consistency (БД остаётся в
согласованном состоянии до и после), Isolation (конкурентные транзакции не видят промежуточные
состояния друг друга — степень регулируется уровнем изоляции), Durability (после коммита данные
переживают сбой).

**В: Code-first vs database-first миграции — плюсы и минусы?**
О: Code-first — схема описывается в коде (сущности/Fluent API), миграции генерируются автоматически,
схема версионируется вместе с кодом в git — удобно для нового проекта и командной работы.
Database-first — схема существует в БД (например, legacy), код генерируется из неё обратным
инжинирингом — нужно, когда БД первична или управляется отдельной командой/DBA.

**В: Что такое индекс и когда он не помогает, а вредит?**
О: Структура, ускоряющая поиск по колонке(ам) за счёт дополнительного места и замедления записи
(INSERT/UPDATE/DELETE должны поддерживать индекс в актуальном состоянии). Вредит, когда на таблицу
много записи и почти нет выборок по этой колонке, или когда индексов слишком много и перекрывают друг
друга.

**В: Как ORM защищает от SQL-инъекций и когда эта защита не работает?**
О: ORM параметризует значения автоматически (LINQ-выражение не собирает SQL строкой с конкатенацией
пользовательского ввода). Защита ломается, если разработчик вручную собирает raw SQL строкой с
подстановкой пользовательского ввода (например, `FromSqlRaw($"... {userInput}")` вместо
`FromSqlInterpolated`/параметров) — тогда ORM тут не при чём, ошибка в обходе его механизма.

**В: Чем отличается connection pooling и почему он важен?**
О: Открытие соединения с БД — дорогая операция (TCP + аутентификация). Пул держит открытые
соединения и отдаёт их повторно вместо пересоздания на каждый запрос — резко снижает латентность и
нагрузку на БД при высокой частоте запросов. Большинство ADO.NET-провайдеров включают его по
умолчанию прозрачно для разработчика.
