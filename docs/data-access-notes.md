# Доступ к данным: EF Core vs Dapper, итоги интеграционных тестов

Техническая заметка по итогам реализации backend-блока Jobs/Clips/Tags (`docs/data-layer-plan.md`).
Покрывает два пункта: выбор и обоснование движков работы с БД, и анализ результатов интеграционного
тестирования (найденные дефекты, покрытие, сознательные ограничения).

## 1. EF Core vs Dapper — почему так

| | EF Core | Dapper |
|---|---|---|
| Где используется | Весь CRUD: `JobsController`, `ClipsController`, `TagsController`, `AuthController` | Один путь: `GET /api/admin/jobs-summary` (`JobReportsQueries`) |
| Почему | Change tracking сам формирует INSERT/UPDATE/DELETE из мутаций доменных методов (`Job.AddClip`, `Job.ReplaceTags`); навигации (`Include`) избавляют от ручных JOIN для графа Job→Clips→Tags; схема — код (миграции) | Кросс-пользовательский отчёт не работает с одной агрегатным корнем — это плоская проекция по всем `Job` всех пользователей. Через EF Core это была бы либо проекция без `Include` (эквивалент ручного SQL, но менее читаемая), либо N+1. Один explicit SQL читается и поддерживается проще |
| Чем платим | Накладные на change tracking там, где он не нужен (не критично для этого объёма данных) | Нет compile-time проверки колонок/типов; при изменении схемы Jobs/Clips/Tags запрос может незаметно рассинхронизироваться — нужно синхронизировать вручную |

### Fan-out в Dapper-запросе — сознательно не `LEFT JOIN`

Первая версия `JobReportsQueries` напрашивалась как один `LEFT JOIN Clips` + `LEFT JOIN JobTags/Tags` с
`GROUP BY` и `STRING_AGG`. От неё отказались: `Clips` и `Tags` — два независимых «один-ко-многим» от
`Jobs`, и совместный `LEFT JOIN` даёт декартово произведение строк (клип × тег). `COUNT(DISTINCT c.Id)`
спасает счётчик клипов, но `STRING_AGG(t.Name)` в том же запросе задвоил бы имена тегов на количество
клипов. Решение — два коррелированных скалярных подзапроса (`SELECT COUNT(*) FROM Clips WHERE JobId = j.Id`
и аналогично для тегов через `STRING_AGG`) вместо одного большого JOIN. Проверено вживую: после добавления
1 клипа и 2 тегов отчёт отдал `clipCount: 1` и оба тега без дублей.

## 2. Итоги интеграционного тестирования

13 тестов (`tests/ClipGen.Be.IntegrationTests`), 6 классов, прогон через `WebApplicationFactory<Program>`
на отдельной БД `ClipGenDb_Test` (LocalDB, переключаемой на Azure SQL через `CLIPGEN_TEST_CONNECTION` без
изменения кода). Все 13 — зелёные. Покрытие: аутентификация и границы (401/403), CRUD и JSON-round-trip
(`ProcessingOptions` + вложенный `CropSettings`), каскадное удаление (`Job → Clip`), общий ресурс в N–N
(`Tag`, не удаляется каскадно), владение данными (чужой пользователь не видит/не меняет/не удаляет),
ролевая авторизация админ-отчёта через Dapper.

### Найденные и исправленные дефекты (не всё работало с первого раза)

1. **`DbUpdateConcurrencyException` при добавлении клипа.** `Job.AddClip(...)` добавлял `Clip` в уже
   загруженную навигацию `Job.Clips` (без явного `db.Clips.Add(...)`). EF Core не был уверен, кто генерирует
   `Guid`-ключ, и для сущности, достигнутой через fixup навигации, выбрал `UPDATE` вместо `INSERT` —
   `UPDATE` закономерно затронул 0 строк (сущности ещё нет в базе). **Исправление:** `ValueGeneratedNever()`
   на `Id` у `Job`, `Clip`, `Tag` (их GUID всегда генерируются в фабричных методах домена, не в БД).
   Миграция `FixGuidKeyGeneration` — пустая (чистая метаданность EF Core, без изменений схемы), что
   подтвердило: дело было именно в допущениях change tracking, а не в структуре таблиц.
2. **Enum'ы как числа в JSON.** По умолчанию `System.Text.Json` сериализует enum как число — Swagger/клиент
   должны были бы угадывать коды. Добавлен глобальный `JsonStringEnumConverter`; Swashbuckle сам подхватил
   его и показал в схеме строковые значения (`"Ai"`, `"BlurredBackground"`, …), без отдельной настройки.
3. **Риск конфликта отслеживания при замене тегов.** Первая версия `Job.ReplaceTags` присваивала
   `JobTags` целиком новый список. Для тегов, которые сохраняются между вызовами (тот же `TagId`), это
   давало два разных CLR-объекта с одним составным ключом `(JobId, TagId)` — старый отслеживаемый и новый
   неприсоединённый — что рискует конфликтом отслеживания или лишними DELETE+INSERT. **Исправление:**
   `ReplaceTags` мутирует существующую коллекцию (`RemoveAll` + `Add`) вместо присвоения нового списка.
   Проверено тестом `ReplaceTags_KeepsSharedDropsRemovedAddsNew` — общий тег остаётся, лишний пропадает,
   новый добавляется, без ошибок.
4. **Порядок старта `WebApplicationFactory` против миграции.** Первый прогон тестов падал с «Cannot open
   database ClipGenDb_Test»: обращение к `Factory.Services` запускает **весь** `Program.cs` (включая сид
   ролей/админа) ещё до того, как фикстура успевала мигрировать базу — а базы ещё не существовало.
   **Исправление:** миграция в `DatabaseFixture` теперь выполняется через отдельный `AppDbContext`,
   не связанный с хостом, гарантированно до первого обращения к фабрике.

### Сознательные ограничения покрытия

- Тесты не чистят за собой данные (каждый использует уникальные `Guid`-имена) — это выделенная одноразовая
  тестовая БД, а не БД разработчика; после прогона в ней остаются «мёртвые» строки, что безопасно для этой
  цели, но не годится как общий паттерн для БД, которую видят люди.
- Один collection fixture — тесты одного прогона идут последовательно (без параллелизма), чтобы не гонять
  миграции и общую БД в несколько потоков одновременно.
- Не покрыто: конкурентные одновременные записи (гонки), нагрузочное/перфоманс-тестирование, полный перебор
  каждого правила валидации по отдельности (DTO-атрибуты проверены выборочно, не исчерпывающе).
